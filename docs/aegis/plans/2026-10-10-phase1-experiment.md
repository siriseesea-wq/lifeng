# 砺锋 v2 — 阶段一验证实验 · 实施计划

**Plan** · 2026-10-10 · 状态：待用户复核

**依据**：`docs/aegis/specs/2026-10-10-lifeng-chemistry-socratic-tutor-design.md`（已复核通过）

> **Aegis Visibility**：本计划存在的唯一理由，是把 spec 中"人工骨架 + LLM 措辞能否
> 稳定产出不泄答案、且学生确实推进的提示"这个命题，变成可执行、可判定的实验。
> 它刻意**不做产品化** —— 因为先建平台再验证核心假设，正是原方向文档最大的错误。

---

## 1. Goal

2 周内完成"20 道有机推理题 × 3~5 名化学竞赛生"的对照实验，产出三项数据：

1. **基线推进率** —— 无系统辅助时的自然推进率
2. **实验推进率** —— 第 1~3 层提示后的推进率
3. **泄答案率** —— 第 1~3 层出现答案关键量的比例

并据此按 spec §5.4 的停止条件决定方向是否继续。

## 2. 本计划内的非目标

| 非目标 | 理由 |
|---|---|
| 用户账号 / 多租户 / 付费 | 3~5 名学生，实验者手工管理 |
| 心理 / 计划 / 复习 / 计时模块 | 与验证命题无关 |
| 自动化卡点判定 | n=20，人工判定比构建判定器更可靠且更便宜 |
| 题库管理后台 | 20 题用 YAML 文件，可 diff、可版本控制 |
| 生产级部署 / 高可用 | 实验期间实验者本地运行 |
| 掌握度建模 / 知识图谱 | spec §2.2 已排除 |

## 3. Architecture

```
problems/p001..p020.yaml   题目 + 骨架（人工标注，纳入版本控制）
        │
        ▼
   models.py  解析为 Problem / Skeleton / 卡点 / 答案关键量清单
        │
        ▼
   hint_engine.py  输入(骨架 + 学生本次尝试 + 目标层级) → 产出提示文本
        │
        ▼
   leak_check.py   黑名单校验；命中 → 重生成；连续命中 → 降级为手写兜底提示
        │
        ▼
   app.py (Streamlit)  学生界面：题目 / 输入尝试 / 逐层取提示
        │
        ▼
   store.py (SQLite)   记录每次尝试、请求的层级、是否推进（人工回填）
        │
        ▼
   analyze.py  产出 §1 的三项指标
```

**关键设计取舍**：n=20 时，**人工判定优于自动判定**。
不为 20 道题构建卡点判定器 —— 实验者阅读 20×5 份对话记录即可完成判定，
且质量远高于任何自动判据。这砍掉了本计划最大的一块潜在过度建设。

## 4. Tech Stack

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.11+ | 本机 3.14.7 已就绪 |
| 存储 | SQLite（`sqlite3` 标准库） | 零依赖，数据量极小 |
| 题库存放 | YAML 文件 + PyYAML | 人工可读可写、可 diff、支持中文与注释；标注是人工密集型工作，可读性优先于少一个依赖 |

| 界面 | Streamlit | 最快到达可用；DeepTutor / 活书同栈，可参考 |
| 环境 | `venv` + `requirements.txt` | 隔离既有项目 |

**依赖清单**：`pyyaml`、`streamlit`、`openai`（走 DeepSeek 兼容端点）。

### T1 · 冻结骨架格式与领域模型

| 项 | 内容 |
|---|---|
| Files | `lifeng/models.py`、`docs/skeleton-format.md`、`problems/p001.yaml`（样例） |
| 目的 | 冻结 YAML schema 与内存模型；后续全部任务依赖它 |
| 最小改动 | dataclass：`Problem`、`Skeleton`、`Pitfall`；`load_problem(path) -> Problem` |
| 兼容影响 | 无 |
| 验证 | `python -c "from lifeng.models import load_problem; p=load_problem('problems/p001.yaml'); print(p)"` 能正确打印样例题 |

**schema 要点**（写入 `docs/skeleton-format.md`）：

```yaml
id: p001
domain: organic            # organic|physical|structural|inorganic|analytical
type: reasoning            # reasoning|memory   ← C2 的分流依据
statement: |
  题干……
answer: |
  参考答案……
key_quantities:            # ← C1 的黑名单来源：答案关键量
  - "1,2-加成"
  - "碳正离子重排"
skeleton:
  insight: "关键洞察一句话"
  pitfalls:
    - trigger: "学生把亲核试剂写成亲电试剂"
      next_step: "回到电子效应判断"
      common_wrong_path: "直接套用课本反应式"
```

### T2 · 会话日志与存储

| 项 | 内容 |
|---|---|
| Files | `lifeng/store.py` |
| 目的 | 持久化每次尝试与提示层级，供 T9 分析 |
| 最小改动 | 建表 `sessions(id, problem_id, student_code, started_at)`、`attempts(id, session_id, level_requested, attempt_text, hint_text, leaked, created_at, progressed)` |
| 兼容影响 | 无 |
| 验证 | 调用 `store.log_attempt(...)` 后 `sqlite3 store.db "select count(*) from attempts"` 递增 |

> `progressed` 字段由实验者事后回填 —— 即 §3 的"人工判定"。

### T3 · 提示阶梯引擎

| 项 | 内容 |
|---|---|
| Files | `lifeng/hint_engine.py` |
| 目的 | 按层级生成提示，**前三层不得给出答案** |
| 最小改动 | `generate_hint(problem, attempt_text, level) -> str`；level ∈ {1,2,3,4}；4 才允许给答案与复盘 |
| 兼容影响 | 无 |
| 验证 | 对样例题分别请求 level=1..4，人工检查：1~3 层是否只提问/给方向，4 层是否含完整答案 |

**prompt 约束**：

- **level 1~3**：只注入 `skeleton.insight`、当前卡点、以及"只可推进到第 N 层"的指令；
  **不注入 `answer` 与 `key_quantities`** —— 这是防泄漏的第一道防线：
  模型看不到答案就不会说出来。（level 1 只给方向，level 3 才给到 `next_step` 的具体动作。）
- **level 4**：**必须注入 `answer`**，否则无法给出完整答案与复盘。
  层 4 不受 C1 约束（C1 只约束第 1~3 层）。

### T4 · 泄答案校验器

| 项 | 内容 |
|---|---|
| Files | `lifeng/leak_check.py`、`tests/test_leak_check.py` |
| 目的 | C1 的落地：第 1~3 层输出命中 `key_quantities` 即判为泄漏 |
| 最小改动 | `is_leaked(hint, key_quantities) -> bool`；大小写/全半角归一化后做子串匹配 |
| 兼容影响 | 无 |
| 验证 | `pytest tests/test_leak_check.py`；边界用例：完全命中 / 部分命中 / 不命中 / 中英文标点差异 |

**已知局限（必须记录）**：黑名单是**字符串匹配**，无法拦截改述型泄漏
（例如把"碳正离子重排"说成"中间体发生骨架变化"）。
n=20 时的对策是**实验者逐条人工复核全部提示**，而非构建 LLM 判定器。
若阶段二规模扩大，此处是明确的技术债。

### T5 · 学生界面

| 项 | 内容 |
|---|---|
| Files | `lifeng/app.py`、`requirements.txt`、`README.md` |
| 目的 | 让学生能独立完成"看题 → 输入尝试 → 逐层取提示" |
| 最小改动 | Streamlit 单页：选择题号 → 显示题干 → 文本框输入尝试 → "给提示"按钮逐层解锁 → 显示提示 |
| 兼容影响 | 无 |
| 验证 | `streamlit run lifeng/app.py` 后在浏览器完成一次完整交互；`store.db` 中出现对应记录 |

**刻意不做**：登录、账号、权限、题目搜索、历史回看、美观主题。

### T6 · 标注 20 道有机推理题（关键路径 · 内容工作）

| 项 | 内容 |
|---|---|
| Files | `problems/p001.yaml` ~ `p020.yaml` |
| 目的 | 产出实验的核心材料；**这是全计划成本最高、也最不可替代的一步** |
| 最小改动 | 按 T1 schema 逐题标注：题干、参考答案、`key_quantities`、insight、3~4 个卡点 |
| 兼容影响 | 无 |
| 验证 | `python -c "..."` 遍历 20 个文件全部可解析；人工确认每题卡点数量 ≥3 |

**工作量估计**：约 5~8 分钟/题 × 20 题 ≈ **2~3 小时**，集中在有机机理。
选题要求：**推理型**（机理、合成推断），**排除记忆型**（C2）。

### T7 · 实验协议与基线方案

| 项 | 内容 |
|---|---|
| Files | `docs/experiment-protocol.md` |
| 目的 | 冻结测量方法，避免事后解释数据 |
| 最小改动 | 写明：被试、题目分配、基线测法、推进判定规则、记录方式 |
| 兼容影响 | 无 |
| 验证 | 文档完成且实验者可据此独立执行 |

**必须解决的实验设计问题**（否则数据无解释力）：

| 问题 | 本计划方案 |
|---|---|
| 基线与实验用同一批题会产生学习效应 | **题目分半**：A 组 10 题先测基线再用系统，B 组 10 题反之；两组轮换以抵消题目难度差异 |
| "越过卡点"由谁判定 | **实验者人工判定**，以骨架中该卡点的 `next_step` 为判据（见 §3 取舍） |
| 基线时学生是否会去查资料 | 协议要求限时、无外部资料、录音/录屏可选 |

### T8 · 执行实验

| 项 | 内容 |
|---|---|
| Files | `store.db`、`docs/experiment-log.md` |
| 目的 | 产出原始数据 |
| 最小改动 | 3~5 名学生，每人 A/B 两组各 10 题，按 T7 协议执行 |
| 兼容影响 | 无 |
| 验证 | 记录条数 = 学生数 × 20（含基线与实验两阶段） |

**前置检查**：运行前确认 §14 的合规项已落实（未成年人数据）。

### T9 · 分析脚本与判定

| 项 | 内容 |
|---|---|
| Files | `lifeng/analyze.py`、`docs/phase1-result.md` |
| 目的 | 产出 spec §5.3 的三项指标并给出判定 |
| 最小改动 | 读 `store.db`，输出：基线推进率、实验推进率、各层推进率、泄答案率、骨架未命中率 |
| 兼容影响 | 无 |
| 验证 | `python -m lifeng.analyze` 输出报告；数字与人工抽查的记录一致 |

**判定规则**（依 spec §5.4）：
实验推进率 **>** 基线推进率 → 继续；
**≤** → 方向重估，不进入平台建设。
泄答案率必须为 0；记忆型题误入引导流程必须为 0。

## 11. Verification（整体）

| 层次 | 手段 |
|---|---|
| 单模块 | `pytest tests/test_leak_check.py`；各任务的 §10 验证命令 |
| 集成 | 完整跑通一次"选课 → 输入尝试 → 请求 4 层提示 → 数据落库" |
| 端到端 | 20 题 × 1 名内部试用者全流程，人工复核全部提示的泄漏情况 |
| 实验级 | T9 的三项指标 + spec §5.4 判定 |

**证伪条件（明确写下）**：若实验推进率不高于基线，则本方向失败。
不得通过调整阈值、扩大题量、或改判据来挽救结论。

## 12. Risks

| # | 风险 | 对策 |
|---|---|---|
| R1 | 20 题样本太小，指标不具统计效力 | 本阶段目标是**方向判定**而非度量精度；结论用"是否显著高于基线"表述，不报精确百分比 |
| R2 | 实验者即开发者，人工判定存在主观偏差 | 判定时以骨架 `next_step` 为唯一判据，并保留全部原始记录供复核 |
| R3 | 学生数量不足（<3） | T0 与 T1~T5 并行；**代价已接受**（见 T0 变更记录）。T8 仍硬性要求 ≥3 名被试 |
| R4 | 黑名单拦截不了改述型泄漏 | 已列为已知局限；n=20 靠人工复核兜住 |
| R5 | 骨架标注质量不稳定 | T6 完成后由实验者自查一遍所有卡点是否"真的能卡住人" |
| R6 | 未成年人数据合规 | 见 §14 |

## 13. Retirement / 后续

- **无退役项** —— 全新项目，不删除任何既有路径。
- 若实验通过：T5 的 Streamlit 界面、T1 的 YAML 题库格式均可在阶段二延续；

- 若实验失败：`~/ZSH/lifeng/` 整体归档，不进入阶段二。**写代码的时间损失约 1 周，
