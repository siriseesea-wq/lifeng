# 骨架 YAML 格式（Schema v1）

> T1 产物 · 2026-10-10 · 冻结后由 T2~T5 共同依赖。
> 对应实现：`lifeng/models.py`。
> 校验入口：`python -m lifeng.models problems/`

---

## 1. 为什么用 YAML 文件而不是数据库

阶段一共 20 道题，标注是**人工密集型**工作。YAML 的优势在这个规模上压倒一切：

- 人工可读可写，支持多行文本与注释
- 可 `git diff`，标注错误可追溯、可回滚
- 无需管理后台（计划 §2 已明确不做题库后台）

进入阶段二（学生数增加）时需评估 SQLite 的并发与隔离，
但**不需要迁移到服务端** —— 数据留本机（见 Design Spec ADR-001 修正）。

## 2. 字段定义

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | str | ✅ | 唯一标识，如 `p001`。目录内不得重复 |
| `domain` | enum | ✅ | `organic` / `physical` / `structural` / `inorganic` / `analytical` |
| `type` | enum | ✅ | `reasoning` / `memory` —— **C2 的分流依据** |
| `statement` | str | ✅ | 题干 |
| `answer` | str | ✅ | 参考答案 |
| `key_quantities` | list[str] | 推理型必填 | C1 泄漏黑名单，见 §3 |
| `skeleton` | mapping | 推理型必填 | 见 §4 |
| `skeleton_source` | enum | 否 | `human` / `ai`，默认 `human`。见 §2.2 |

### 2.2 `skeleton_source` 为什么必须存在

Design Spec 的决策 4 是「**人工**标注骨架 + LLM 措辞」——
实验要验证的正是这个组合。

若骨架由 AI 生成，验证的命题就变成了「LLM 骨架 + LLM 措辞」，
**那是另一个命题**。

所以 AI 出的题必须标 `skeleton_source: ai`。否则将来真做实验时，
无法说明参与验证的骨架里有多少条不是人写的，结论也就无从解释。

用 `python -m lifeng.generator` 生成的题会自动带上这个标记。

### 2.1 `type` 的语义（对应 C2）

| 取值 | 含义 | 系统行为 |
|---|---|---|
| `reasoning` | 需要推理才能得出答案（有机机理、合成推断、物化建模） | 进入提示阶梯 |
| `memory` | 靠记忆（元素化学、人名反应、试剂特性） | **不进引导流程**，走卡片检索 |

**判定原则**：问自己"我能用提问让学生自己想到吗？"
能 → `reasoning`；不能 → `memory`。

这条判定是硬边界。把记忆型题标成推理型，产品会在该题上出现
"连问三轮，学生只能说'我就是不知道'"的体验崩塌。

## 3. `key_quantities` —— C1 黑名单的取舍（解决 Spec §9 开放问题 1）

**规则：只放「最终答案」，绝不放「中间机理」。**

| 该放 | 不该放 |
|---|---|
| 最终产物名（频哪酮） | 中间体名（叔碳正离子） |
| 产物的系统命名（3,3-二甲基-2-丁酮） | 机理步骤名（1,2-迁移） |
| 最终数值答案 | 稳定化方式（氧鎓共振） |

### 为什么这样切

黑名单的作用是拦住"泄漏答案"。但**机理是教学内容本身**，不是答案。
如果禁止提示提到"迁移"，第 2 层提示就永远推不动学生 —— 校验器会把
所有有效的引导全部误杀。

以 `p001`（频哪醇重排）为例：

- 黑名单 = `[频哪酮, 3,3-二甲基-2-丁酮, pinacolone]`
- 提示可以说："检查这个碳正离子相邻碳上连了什么基团" ✅
- 提示不能说："重排后得到频哪酮" ❌

### 已知局限

`key_quantities` 是**字符串黑名单**，拦截不了改述型泄漏
（把"频哪酮"说成"那个叔丁基酮"）。阶段的应对方式是
**实验者逐条人工复核全部提示**，而不是构建 LLM 判定器 ——
20 道题 × 5 名学生，人工复核比写判定器更快也更准。

若阶段二规模扩大，此处是明确的技术债（见计划任务 T4）。

## 4. `skeleton` 结构

```yaml
skeleton:
  insight: |
    一两句话概括这道题的"关键洞察"。
    它是提示的天花板 —— 任何提示都不得超出它。

  pitfalls:            # 至少 3 个（计划 T6 验收要求）
    - trigger: |
        什么表现说明学生卡在这里。
      next_step: |
        越过该卡点的下一步动作。
      common_wrong_path: |
        学生最常走错的岔路。
```

### 4.1 三个子字段的用途

| 字段 | 用途 | 被谁消费 |
|---|---|---|
| `insight` | 提示生成的上界 | T3 提示引擎 |
| `pitfalls[].trigger` | 卡点定位的匹配依据 | T3 提示引擎 |
| `pitfalls[].next_step` | **推进判定的唯一判据** | T9 分析（人工判定时对照） |
| `pitfalls[].common_wrong_path` | 提示的"反向指路"素材 | T3 提示引擎 |

### 4.2 为什么 `next_step` 是判定判据

计划 §3 已决定：n=20 时由**实验者人工判定**是否推进。
若无统一判据，判定会退化成主观印象，数据失去意义。

因此 `next_step` 必须写得**可观察**：

- ✅ 好的写法："让学生检查该碳正离子相邻碳上连了哪些基团"
  → 可观察：学生的下一次尝试是否提及了相邻基团
- ❌ 差的写法："让学生理解重排的必要性"
  → 不可观察：无法判定"理解"与否

## 6. 校验

```bash
python -m lifeng.models problems/
```

任一文件不合规即报错并指出**文件与字段**。校验项：

1. 必填字段非空
2. `domain` / `type` 取值合法
3. 推理型必须有 `skeleton` 且 `pitfalls` ≥ 3
4. 推理型必须有非空 `key_quantities`
5. 目录内 `id` 不重复
